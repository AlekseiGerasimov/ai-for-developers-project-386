# Файловая H2 и транзакционная блокировка календаря

Для приложения с одним владельцем и одной работающей копией используем файловую H2, Spring JDBC с явным SQL и миграции Flyway. Вместо отдельного сервера PostgreSQL выбираем встроенную БД, чтобы сохранить запуск одним JAR; вместо ORM — явные запросы и управление транзакцией. Путь к БД настраивается, по умолчанию `./data/calendar` относительно рабочей папки; данные находятся вне каталогов сборки и сохраняются после обычного перезапуска. Первый запуск создаёт схему и служебную строку календаря без демонстрационных типов и встреч; тесты используют отдельные временные БД.

Каждое создание встречи выполняется в одной транзакции `READ_COMMITTED`: сначала блокируется единственная строка календаря владельца через `SELECT … FOR UPDATE`, затем по актуальному серверному времени повторно проверяются правила записи, проверяются пересечения всех типов встреч и сохраняется результат. Блокировка сохраняется до commit или rollback; успех возвращается после commit. Строка календаря существует заранее, поэтому защита работает и при отсутствии встреч. Блокировка только найденных встреч не защищала бы пустой календарь; замок в Java привязал бы гарантию к дисциплине синхронизации в процессе. Блокировка календаря намеренно сериализует и непересекающиеся записи: для одного владельца принимаем это упрощение.

Пересечение определяется условием `existingStart < newEnd AND existingEnd > newStart`, поэтому примыкание допустимо. Все пути создания встреч обязаны использовать общий протокол; схема H2 сама по себе не запрещает пересечения при его обходе. Ожидание блокировки ограничено 5 секундами. Таймаут и недоступность БД являются техническими ошибками, а не конфликтом занятого времени; автоматических повторов создания нет. Если commit прошёл, а ответ потерян, встреча может существовать без полученного гостем подтверждения: ответы на повторный запрос определяются в решении об API, идемпотентность здесь не гарантируется.
