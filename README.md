Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Пользовательский сценарий

«Запись на звонок» — упрощённый сервис по мотивам [Cal.com](https://cal.com).
Владелец календаря один и задан заранее; гость записывается без регистрации.
Ниже описан целевой сценарий приложения, которое предстоит реализовать.

1. **Создание типа встречи.** Владелец открывает список типов встреч и создаёт
   «Знакомство»: описание «Обсудим задачу и дальнейшие шаги», длительность 30 минут.
   Сохранённый тип появляется в публичном каталоге встреч.
2. **Выбор встречи.** Гость открывает каталог, выбирает «Знакомство» и видит
   описание, длительность и календарь записи на ближайшие 14 календарных дней.
3. **Выбор времени.** Гость выбирает доступный день, затем свободный слот.
   Например, встреча с началом в 10:00 длится до 10:30. На странице указан
   часовой пояс, чтобы время записи было однозначным.
4. **Подтверждение записи.** Гость вводит имя и email, проверяет тип встречи,
   дату и время и подтверждает запись. Приложение показывает подтверждение
   с деталями встречи. Имя и email — предлагаемые поля для нашего приложения;
   окончательный состав формы будет зафиксирован в спецификации.
5. **Просмотр владельцем.** Владелец открывает общий список предстоящих встреч
   всех типов и видит новую запись: тип встречи, дату, время и данные гостя.
6. **Защита занятого времени.** Интервал 10:00–10:30 больше нельзя забронировать,
   в том числе частично пересекающейся встречей другого типа. Следующая встреча
   может начинаться в 10:30. Если два гостя одновременно подтверждают
   пересекающиеся интервалы, запись получает только один; второму предлагается
   выбрать другое свободное время.

В проект не входят авторизация, личные кабинеты, внешние календари и уведомления.
Начало 14-дневного окна, рабочие часы, часовой пояс и шаг доступных стартов
будут определены в спецификации, а не на этапе изучения референса.

## Стек

- Бекенд: Java 25 LTS, Spring Boot 4.1.2, Maven Wrapper, JUnit.
- Фронтенд: React, TypeScript, Vite, Mantine.
- Контракт: TypeSpec → OpenAPI 3.0 → Java-интерфейсы и TypeScript SDK.
- Проверки: Checkstyle, ESLint, Prettier, actionlint и npm audit; окружение и задачи — mise, Git-хуки — hk.

## Установка

Установите [mise](https://mise.jdx.dev/getting-started.html) и добавьте его в PATH.
Минимальная версия mise и версии инструментов закреплены в `mise.toml`,
Maven Wrapper и `package-lock.json`.

В `package.json` временные `overrides` закрывают уязвимости зависимостей инструментов;
при обновлении инструментов их следует пересмотреть.

На Windows mise должен быть доступен в обычном терминале и терминале IDE.
После установки добавьте каталог с `mise.exe` в PATH и перезапустите терминал.
Проверка: `mise --version`.

Git-хуки запускают проверки через `mise exec`, чтобы использовать версии
инструментов из `mise.toml`. Сам `mise` должен быть установлен в постоянный
каталог и доступен в PATH процесса Git. После изменения PATH перезапустите IDE.
Для переустановки хуков выполните `mise exec -- hk install --mise`.

```bash
git clone https://github.com/AlekseiGerasimov/ai-for-developers-project-386.git
cd ai-for-developers-project-386
mise trust
mise install
mise run setup
```

## Использование

```bash
mise run dev
```

Откройте http://localhost:5173: страница проверяет соединение с бекендом
через сгенерированный SDK. Бекенд отвечает на http://localhost:8080/api/health.
Vite проксирует `/api` на бекенд. Сейчас реализован только каркас,
без бронирования и базы данных.

Серверы работают в фоне под управлением mise/pitchfork:

```bash
mise daemons status
mise daemons logs backend
mise daemons stop backend frontend
```

Команды из корня репозитория (Windows и Linux):

| Команда                       | Назначение                                                    |
| ----------------------------- | ------------------------------------------------------------- |
| `mise run install`            | Установка npm-зависимостей из lockfile без Git-хуков (для CI) |
| `mise run check`              | Генерация, линтеры, типы, сборка и smoke-тест                 |
| `mise run lint`               | Checkstyle, ESLint, Prettier и actionlint                     |
| `mise run lint:commit`        | Те же линтеры с Maven offline после начальной установки       |
| `mise run audit`              | Сетевой аудит npm, ошибка при high/critical                   |
| `mise run test`               | JUnit: запуск сервера и HTTP-запрос к `/api/health`           |
| `mise run build`              | Сборка фронтенда и исполняемого JAR                           |
| `mise run generate`           | Обновление OpenAPI и клиентского SDK из TypeSpec              |
| `mise exec -- npm run format` | Форматирование исходников и конфигураций                      |

Контракт находится в `contracts/main.tsp`, сервер — в `backend/`,
интерфейс — в `frontend/`. После изменения TypeSpec выполните генерацию
и включите обновлённые `contracts/openapi.yaml` и `frontend/src/api/` в коммит.
Java-интерфейсы генерируются при Maven-сборке в `backend/target/`.

GitHub Actions запускает `mise run check` на каждый push и pull request.
`mise run setup` предварительно загружает зависимости линтера и устанавливает Git-хуки.
Pre-commit вызывает только `mise run lint:commit`, без сборки, тестов и сетевых запросов;
commit-msg проверяет Conventional Commits, например `feat: add meeting types`
или `chore: scaffold application`. Автоматические релизы пока не подключены.

### Проверка перед коммитом и Maven-кэш

`mise run lint:commit` запускает Checkstyle с флагом Maven `--offline`, чтобы
проверка перед коммитом не обращалась к сети. Для этого инструменты должны быть
установлены, а зависимости Maven — уже загружены. Первоначальный `mise run setup`
выполняется с доступом к интернету: он устанавливает npm-зависимости, запускает
линтеры онлайн для заполнения Maven-кэша и затем устанавливает Git-хуки.

Если очистить `~/.m2` (на Windows — `%USERPROFILE%\.m2`), offline-проверка может
завершиться ошибкой о недоступном в кэше плагине или зависимости. Подключитесь
к интернету и выполните из корня проекта:

```bash
mise run lint
mise run lint:commit
```

Первая команда разрешает Maven скачивать недостающие зависимости; вторая
проверяет, что линтеры снова работают без сети. После успешной проверки повторите
коммит. Переустанавливать npm-зависимости и Git-хуки для восстановления Maven-кэша
не требуется. При обновлении Maven-плагинов также сначала выполните `mise run lint`.

Аудит зависимостей вынесен из `check` в отдельный workflow: каждый понедельник
и вручную через GitHub Actions. `mise run audit` проверяет также devDependencies
и завершается с ошибкой при уязвимостях high/critical. Новые CVE не блокируют
обычный прогон проверок приложения.

Основа создана по официальным инструкциям [Spring Boot](https://spring.io/guides/gs/spring-boot),
[Vite](https://vite.dev/guide/) и [Mantine](https://mantine.dev/guides/vite/).
